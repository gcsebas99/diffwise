## HARNESS:CONTEXT

- **Structured diff model: files → hunks → lines with new-side line numbers.** — `src/core/diff.ts:1`
  WHY: the agent gets numbered, per-file hunks through tools instead of one raw patch, so it
       can cite exact lines and pull only the files it needs.
  INTERVIEW: "Why not paste the diff?" → token cost, attention dilution, and the model can't
             reliably count lines in raw patch text; structured data can be validated.
- **Print the new-side line number on every line instead of raw +/- patch text.** — `src/core/tools/get-file-diff.ts:46`
  WHY: models are unreliable at counting lines from a hunk header; printing the number makes
       "report line 9" a copy, not arithmetic, and that is the number report_finding checks.
- **Truncate tool output at a line boundary and say how to get the rest.** — `src/core/tools/util.ts:5`
  WHY: one huge file or search can fill the context window and push out the task itself; a hint
       ("…[312 more lines; narrow the range]") turns the cut into a next step, not a dead end.

## HARNESS:GUARD

- **Only new-side lines (added or context, inside a hunk) are commentable.** — `src/core/diff.ts:9`
  WHY: findings are published as GitHub review comments with side=RIGHT; a line outside the
       diff gets a 422, and one bad comment fails the whole review request.
  INTERVIEW: "How do you stop comments GitHub will reject?" → validate line against the
             diff model in report_finding, before anything reaches the API.
- **git runs via execFile with an argument array, never a shell string.** — `src/core/local-git-source.ts:86`
  WHY: patterns, paths and refs come from the model or the PR; in a shell string, a value like
       "x; rm -rf ~" or "$(curl …)" would execute. As an array element it's just text.
  INTERVIEW: "How do you run tools on untrusted input?" → no shell, `--`/-e/--end-of-options
             separators, timeouts and output caps, read-only commands only.
- **Validate the rules file at the boundary and fail loudly, listing every problem.** — `src/core/rules.ts:137`
  WHY: it's external input from the target repo, and a bad rule can't be fixed mid-review.
       Stop before any model call, with errors the author can act on.
  INTERVIEW: "Config errors vs tool errors?" → config: fail fast at startup (a human fixes it);
             tool args: return the error to the model (it can correct itself in the loop).
- **Tool paths must be repo-relative: no absolute paths, no ".." segments.** — `src/core/tools/util.ts:24`
  WHY: paths come from the model, which can be steered by PR content ("read ../../.ssh/id_rsa").
       LocalGitSource reads git objects only, but the check belongs at the tool boundary so a
       future source (e.g. a plain filesystem) can't be tricked either.

## HARNESS:TOOLS

- **A tool description is a prompt: when to call it, what the output means.** — `src/core/tools/list-changed-files.ts:10`
  WHY: the model knows nothing beyond name + description + schema. "Call this first" and
       "a file with no rules needs no findings" steer behavior more than any system prompt line.
  INTERVIEW: "How do you get an agent to use tools well?" → write descriptions like docs for a
             new teammate, name the next tool to use, explain every symbol in the output.
- **One Zod schema per tool, both the API's JSON Schema and the validator.** — `src/core/tools/registry.ts:20`
  WHY: what the model is told and what execute() enforces can't drift apart.
       io:"input" describes what the caller may send (fields with defaults aren't required).
- **execute() never throws: every failure becomes ok=false with a next step.** — `src/core/tools/registry.ts:34`
  WHY: the loop must keep running so the model can self-correct; a crash would lose the
       whole review over one bad call. Retries are bounded by the loop's step cap (1.8).
  INTERVIEW: "Where do you validate tool calls?" → at one choke point, before run(); the
             model's arguments are untrusted input like any other.
- **Tool failures are values: ok=false becomes is_error on the tool_result.** — `src/core/tools/types.ts:7`
  WHY: a thrown error ends the review; a returned error lets the model read why and retry
       with corrected arguments on its next turn.
  INTERVIEW: "What happens when the model calls a tool wrong?" → validate, return an actionable
             error as the tool result, let it self-correct; the step cap bounds retries.
